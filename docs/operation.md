# Operating Shipfloor

The commands, the dashboard, where the logs are, and how to run the tests. Back to the [README](../README.md).

## Operation

`shipfloor dashboard` · `shipfloor list` · `shipfloor pool` · `shipfloor pause [project]` · `shipfloor resume [project]` · `shipfloor remove <project>` · `shipfloor metrics <project>` · `shipfloor clean <project>` · `shipfloor accept <project> <n> <reason>` (owner only: after reviewing how a card's acceptance test files changed since the QA commit, for example a merge from main resolved by hand, take them as they stand; `acceptance-intact` then passes those exact contents, recorded in `~/.shipfloor/projects/<project>/accepted.tsv`, and blocks again on any later edit). Before it comes to that, a card's own QA gets the first word: an engineer who finds an acceptance test wrong reports it instead of editing it, and when `acceptance-intact` fails on the card's own edit the Tech Lead sends the test back to QA, who either corrects it or puts it back and says what the code must do. QA's correction is a new QA commit, which becomes what the gate protects, and `gate.sh qa-amend <n>` keeps it honest without anyone reviewing it first: it touches only test files, loses no assertion line, switches no test off, and a card is amended at most twice. For one more, the owner adds the label `qa-amend-ok` to the issue, or presses "Approve this amendment" on the blocked card in the dashboard (it adds the label and unblocks the card); the label is spent on that one commit. The amendment is commented on the issue and listed in the report.
`shipfloor dashboard` (or `/sf:dashboard` inside Claude Code) opens a local page with the pool, live runs, logs (per card, and a Logbook view, with History's totals at its top, and every run, what it left behind and the dispatcher's log in one timeline), the estimated cost of each card and the review pages, where Spec Review and Staged cards are approved or sent back. Its address carries a random token; `--token <text>` fixes it instead. The In progress panel lists every card in the factory's hands: the sessions at work and, marked as waiting with the reason (a busy stage slot, a pause), the cards that wait for a run. Every panel, and every running session, has a maximize button in its corner that opens it over 90% of the screen: the lifecycle line becomes a board with each card by name in two lanes (upstream, to an approved spec; downstream, to production), and History lists the period's runs one by one and its cards by estimated cost. History opens on today and takes a period of its own (Today, 7 days, 30 days, or two dates up to 92 days apart, kept in the browser): its totals against the period before, the runs and the spend by hour or by day (a day opens by hour), and how long each stage took; the header's figures stay about today. What waits for you, maximized, is a decision inbox: the queue with the oldest wait first, what to read to decide the card in focus (the spec's problem, acceptance criteria and open questions from its review page; a pull request's size and checks; a block told in order: the step it stopped at, why, how the acceptance tests changed since QA wrote them, what the factory tried) and the decision as options that each say when to choose them and where the card goes next. A blocked card can be retried, sent back to Coding with a note, or, when `acceptance-intact` stopped it, have its tests taken as they stand (`shipfloor accept`). A decision leaves as soon as it is made. In the maximized lifecycle the owner also moves their own cards by dragging them, or with `M` and the digit a column shows, or the Move button on a touch screen: Inbox to Ready for Refinement and back, a spec approved or sent back, a Ready for Dev card refined again, a staged PR shipped or sent back to Coding (a note is required to send a card back). A card with a run in progress or blocked by infrastructure shows a lock and does not move. A card blocked for the owner can be taken back the same way, with an optional comment posted on the issue: to Ready for Dev to redo the code from the approved spec (only when it was blocked in Coding or Validation), to Ready for Refinement to refine the spec again, or to the Inbox to take it out of the factory, which closes its pull request and keeps the branch; the block comes off with the move, and "Unblock & retry" stays on the card. In Inbox, Ready for Refinement and Ready for Dev each card shows its place, and dropping a card on another one of its column (or the arrow keys while it is held) puts it before that one: the order is written to the GitHub Project and the dispatcher takes cards from the top. A card moved into one of those columns from the dashboard goes last. Every move and reorder leaves as soon as it is made, and a card moved into a column the factory acts on wakes the dispatcher, so it starts within seconds. The Settings view changes this machine's limits (the pool, each stage's slots, the stacks; saved to `~/.shipfloor/config.yml` and read on the next cycle) and pauses the factory or one project at once; For a project it also sets how the factory operates on it on this machine (cards in progress and specs in refinement at once, how long the deploy waits, the largest conflict an agent may resolve) and, in Settings > Language, the language the factory writes in for it (specs, pull requests, comments, reports, gate messages), apart from the dashboard's own: these are kept in `~/.shipfloor/projects/<project>/overrides.yml`, which every config reader lays over the project's `factory.yml`, and nothing else can be overridden there. A language change applies from the dispatcher's next cycle: a run already going keeps the language it started with (`FACTORY_LANGUAGE`, set at launch), and `shipfloor doctor` says each project's language and whether it comes from the repository or this machine. What a project is (its files, layers and commands) is shown as the dispatcher last read it, with the file to edit in its repository. A card's Live tab shows its latest session as it happens (what the run and its subagents say and do) and, while a run works on the card, takes a message for it: the run and each of its subagents read the message after the tool call they are in (a hook the plugin ships, `hooks/hooks.json`), and no run ever waits for one. A Codex run gets it the same way, through the hook that `shipfloor install` generates in the factory's `CODEX_HOME` (`inbox_hook.py --codex`); the first session to call the hook is the lead and any other is a subagent, each reading a message once. There is no other path for Codex: no inbox file for the agent to poll. A Codex run's Live shows its messages, commands and the owner's messages the same way, and its Sessions list the models and the subagents' tokens; the cost is `$ ?` for a model without a price in `prices.yml`.

**The day in replay.** Under the belt a scrubber covers today, with a mark for each run that ended (ok or bad) and each decision you took. Drag the needle, or use the keys (Home goes to today's first board record, Left and Right move 5 minutes, PageUp and PageDown an hour, End goes back to now), and the belt shows the board as it was at that time, drawn from `~/.shipfloor/projects/<project>/logs/board-<YYYY-MM>.jsonl`; before the first record of the day it says there is no history for that hour. While a past hour shows, the page is a replay: it stands still and every decide control is off, until you press "Back to live". The Logbook view shows the same marks as lines and keeps the period's totals at its top.

**The tab, the address and Ctrl K.** The dashboard says what waits for you even from a pinned tab: the title reads `(N) Shipfloor · <project>` while N decisions wait in the project on screen, and `Shipfloor · <project> · stopped` (in the dashboard's language) when the dispatcher went silent; the icon turns to the accent color while something waits and to the bad color while the factory is stopped (stopped outranks waiting), and stays neutral otherwise. A replay does not change them. Selecting a card in the work area writes `#card/<n>` to the address (never the token), so Back returns to the previous selection and a link to `#card/<n>` opens with that card selected; an address for a card that does not exist, or one that is malformed, shows the default view. `#@HHMM` stays the replay's time. The page keeps the link's token in this browser (`shipfloor.token`), so an address without `?t=` opens on the last token it had. Ctrl K (Cmd K on macOS) or the Commands button in the header opens a palette with one field and at most nine results: the actions the page offers at that moment (Next decision, Pause the factory, Back to live during a replay, and See the line at a time you type, like `9:40`) and cards matched by number (`120` or `#120`) or a word of the title, each with its column; Enter runs the active row exactly as the matching button would, Esc closes it and the focus goes back to where it was.

**The push link.** When ntfy is configured and the dashboard is running, a push for a card waiting for you (its wait and reminder messages) carries a `Click` header, `http://127.0.0.1:<port>/#card/<n>`, which opens that card. The port is the one the running dashboard bound, read from `~/.shipfloor/dashboard.port` (one line, written after the bind and removed on a clean exit); without it the push goes out with no link. The link only works when it is read on the same machine that runs the dashboard, because the dashboard stays on 127.0.0.1 and is not reachable from a phone or another computer; it carries no token (the page uses the one it saved in the browser), and a stale `dashboard.port` after a crash only yields a link that does not load.

The dashboard link's secret is kept in `~/.shipfloor/dashboard.token`, so a link from an earlier run still opens the dashboard after a restart; deleting that file and restarting makes a new link (the old one is then refused).
Logs in `~/.shipfloor/logs/dispatcher.log` and `~/.shipfloor/projects/<project>/logs/`. A layer may set `install` (for example `pnpm install --frozen-lockfile`): the gates run it in the layer's directory before its build or tests, once per content of that directory, so no agent has to install a worktree's dependencies; a failing install is exit 3 (infrastructure). A project the dispatcher cannot use in a cycle (its control checkout does not reach `origin/<main>`, or the config there is missing or invalid) is skipped: the reason and the time of the first failed cycle go to `~/.shipfloor/projects/<project>/SKIPPED`, the dashboard shows a "skipped since" flag and `shipfloor doctor` warns; the first good cycle clears it. An `index.lock` older than 10 minutes in the control checkout (`SHIPFLOOR_STALE_LOCK_MIN`) is treated as left by a dead git and removed. Reports on each repository's orphan `factory-reports` branch. At the end of every cycle the dispatcher empties what cards left under the project's `tmp/`: the `tmp/<n>/` of a card that is Done or off the board, and stray files or folders beside them once nobody touched them for 3 days, unless their name carries the number of a card still in progress (`shipfloor clean <project>` does the same on demand).

Every dispatcher cycle appends one line to `~/.shipfloor/logs/health-<YYYY-MM>.jsonl`: each project's cards per column and blocked cards, runs against the pool and the stage slots, busy stacks, the machine's CPU, free memory and free disk, and how the cycle went (seconds, exit code, whether another cycle was still running). The dashboard and `shipfloor doctor` raise what the last three cycles show: a stage with a free slot and cards waiting through all three, more runs than a limit, two cycles at once. A card that waits on a dependency (below) is not counted as waiting there.

**Dependencies.** To make a card wait for another, add the other issue to its "Blocked by" relation on GitHub (the issue's sidebar, Relationships). Text in the issue body, such as "depends on #12", is not read. Before it starts a Coding, Validation or Deploy run (never a refinement), the dispatcher asks GitHub once per candidate per cycle for the issues it is blocked by (`gh api repos/<repo>/issues/<n>/dependencies/blocked_by?per_page=100`). While one of them is open, or when the read fails, the card is not started: it gets no label, takes no slot and does not count as a failed cycle, and the next cycle asks again. A dependency that is closed, merged or closed as not planned, never blocks. What the dispatcher read is kept in `~/.shipfloor/projects/<project>/deps.json`; the dashboard shows it in the card's drawer ("Depends on", each dependency in its column) and in the reason a card waits, and says when the dependencies could not be read. The dashboard asks GitHub nothing.

The demo: `bash scripts/test/demo-stack.sh up` serves this checkout's dashboard on sample data (two projects, every kind of card and run) and prints its address, `http://127.0.0.1:<port>/?t=<token>`; `down` stops it and removes its files.
It reads only `SHIPFLOOR_STACK` (default `shipfloor-demo`), `SHIPFLOOR_PORT_WEB` (7727) and `SHIPFLOOR_DEMO_TOKEN` (`demo`), never touches `~/.shipfloor` and never calls the real `gh`, so a card that changes the page can be looked at without a factory home.

## Development

`bash scripts/test/run.sh` runs the suite; `bash scripts/test/run.sh --changed` runs only the tests tied to what changed against `origin/main` (use it while editing, and the whole suite before a push). Designs in `docs/superpowers/specs/`. The logic lives in `scripts/shipfloor_core/`; the `.sh` files are wrappers, and `scripts/test/hygiene.test.sh` fails when a line of logic lands in one. `docs/contracts.md` names the module behind each script.
